# Asset pipeline documentation

`pipeline.yaml` is the master record of how assets get made. Most of this
directory is generated from it. One part — `backlog/` — runs the other way: it is
hand-authored input that turns into GitHub issues.

| File | What it is |
| --- | --- |
| [`pipeline.yaml`](pipeline.yaml) | **Source of truth.** Edit this. |
| [`PIPELINE.md`](PIPELINE.md) | Generated. The readable version, with a flowchart and the screenshots. |
| `backlog/` | **Hand-authored input.** A queue of issues to open, one file per issue template. Not generated; not overwritten. |
| `images/` | Screenshots, extracted from the original Miro board. |
| [`../file-naming-spec.md`](../file-naming-spec.md) | Generated by hand. The naming conventions on one page, summarised from `pipeline.yaml`. |
| [`../SolarPunk Jam - Asset Pipeline.svg`](../SolarPunk%20Jam%20-%20Asset%20Pipeline.svg) | The Miro export this was derived from. Historical; no longer maintained. |

Read [`PIPELINE.md`](PIPELINE.md) if you just want to know how to deliver an asset, or
[`../file-naming-spec.md`](../file-naming-spec.md) if you only need to know what to call it.

## Why this exists

The Miro board drew five phases left to right with a single "Repeat" arrow, so it
read as a sequence. It isn't one — every phase is re-entered and assets flow
backwards constantly. It was also unusable by anything but a human: the naming
conventions it documented lived only as pixels, while CI enforced its own
separate copies of similar rules.

`pipeline.yaml` fixes both. Loops are first-class (`phases[].loop` and typed
`edges`), and the conventions are machine-readable, so CI can check that the
document and the code still agree.

## Editing it

1. Edit `pipeline.yaml`. Your editor will offer completion and inline errors from
   the schema via the `# yaml-language-server:` comment at the top of the file.
2. Validate and re-render:

   ```bash
   pip install pyyaml jsonschema

   python .github/scripts/validate-pipeline-doc.py
   python tools/pipeline/pipeline.py render pipeline
   python tools/pipeline/pipeline.py render issue-templates            # report
   python tools/pipeline/pipeline.py render issue-templates --write
   ```

   `pipeline.py --help` lists every command; each takes `--check` or `--write`.

3. Commit `pipeline.yaml` **and** the regenerated `PIPELINE.md`. CI fails if they
   disagree.

`.github/workflows/validate-pipeline-doc.yml` runs all of the above on any PR
that touches this directory, the schemas, the tooling, or the scripts whose
constants the document mirrors.

## What the validator checks

Beyond the JSON Schema at [`schemas/asset-pipeline.schema.json`](../../schemas/asset-pipeline.schema.json):

- every edge endpoint resolves to a real step, and every step is reachable from
  the pipeline's `entry_step`
- **at least one phase declares `loop.is_iterative`**, and an authoritative
  pipeline has at least one `rework` or `repeat` edge — the guard against this
  document quietly collapsing back into a flat sequence
- every screenshot resolves to a declared image whose file exists and whose
  sha256 still matches, and no image is declared without being used
- every `enforced_by` path and `opened_by_issue_template` exists on disk
- every naming `regex` compiles, and its own `examples.valid` / `examples.invalid`
  agree with it
- every entry in `code_mirrors` still matches the constant it mirrors, so a
  convention cannot be changed in a script without changing this document

## Adding a screenshot

Images are files, not base64 — a 400 KB YAML would be unreviewable in a diff.

For a screenshot that is already in the Miro SVG, add its `IMG_n` id to
`IMAGE_NAMES` in [`tools/pipeline/pipeline_cli/images.py`](../../tools/pipeline/pipeline_cli/images.py)
and run the extractor. For a new screenshot, drop the file in `images/` and add
an entry to the `images:` list by hand:

```bash
python tools/pipeline/pipeline.py extract images
python tools/pipeline/pipeline.py extract images --emit-yaml   # prints hashes and dimensions
```

Then reference it from a step's `screenshots:`. Alt text is required, and an
image nothing references is a validation failure.

## Opening issues from the templates

`pipeline.py issue create` builds an issue body from a
[`.github/ISSUE_TEMPLATE/`](../../.github/ISSUE_TEMPLATE) form, so a CLI-opened
issue and a browser-opened one are the same document — generated subtasks
checklist included.

```bash
python tools/pipeline/pipeline.py issue create \
    --template create_model \
    --name "rain barrel" \
    --description "A wooden rain barrel." \
    --field "dimentions=1m x 1m x 1m" \
    --filepath assets/art/3d/props/rain_barrel/sm_rain_barrel.gltf
```

That prints the three `gh` commands it would run and the body it would post.
**Nothing is sent until you add `--apply`** — the same convention as
`tools/fix_audio_filenames.py`.

The filepath is checked against `pipeline.yaml` *before* the issue exists. A
`{placeholder}` still in the path, or a filename that breaks a naming pattern, is
refused rather than warned about: it costs nothing to fix now, and an unusable
path stays on the board forever. `--force` overrides. Required fields must be
answered too — the templates' own defaults are worked examples, and filing "This
hamster is a cheerfull, cartoonish..." verbatim helps nobody.

`issue update <number>` amends one that already exists: `--filepath`,
`--priority`, `--status`, `--title`, labels, `--state`, and
`--resync-subtasks --template <slug>`, which re-renders the generated checklist
inside an issue that is already open. Re-rendering the templates otherwise only
affects issues opened afterwards.

Writes need `gh` and the project scope:

```bash
gh auth refresh -h github.com -s project
```

## Filing a backlog in bulk

`asset_list.tsv` is the *output* direction — what the board already holds. A
backlog file is the *input* direction — what you want it to hold. It is a local
YAML file you fill in offline, in an editor, and then drain into GitHub:

```bash
python tools/pipeline/pipeline.py backlog new --template create_model
# fill in documentation/pipeline/backlog/create_model.yaml
python tools/pipeline/pipeline.py backlog file            # dry run: checks every entry
python tools/pipeline/pipeline.py backlog file --apply    # opens the issues
```

One file per issue template, and the file names its own template, so a backlog
cannot disagree with itself about which form its entries are for. A key
belonging to some other template is a named error rather than a dozen issues
full of `_No response_`.

```yaml
template: create_model

defaults:            # assignee, labels, priority. Any entry may override them.
  assignee: your-github-handle
  priority: high

issues:
  - name: lantern
    description: |
      Hanging lantern for the tavern.
      Must still read at 10 m in the GL Compatibility renderer.
    dimentions: 0.3 m tall x 0.15 m wide
    filepath: assets/art/3d/props/lantern/sm_lantern.gltf
```

`filepath` means the same thing in every backlog, whatever the template happens
to call the field underneath — `file_path` in `create_model`, `context` in
`create_implementation`. Everything else is a field id from the template itself.
`backlog new` scaffolds the required ones; optional fields are named in a comment
and accepted if you add them. The generated subtasks checklist is deliberately
not a key — it already reaches the issue from the template.

**`--apply` writes the issue number back into the entry it came from**, and an
entry that has one is skipped. That makes the command safe to run twice, and
re-running it is exactly how you resume: the number is recorded the moment the
issue exists, so a run that dies partway leaves the numbers it earned on disk and
files only what is left. The backlog file is the ledger; there is no other state.

The write-back is a splice, not a re-emit — one line is inserted and every other
byte stays put, so your comments, block scalars and key order survive it.

Every selected file is validated before anything is sent, so one bad entry holds
up the whole batch rather than filing half of it. Narrow the run with
`--template` or `--from` when that is not what you want.

Unlike the checks above, this is **not** a CI gate: even a dry run resolves the
organization field ids over the network to show the commands it would run.

## The asset list

[`asset_list.tsv`](asset_list.tsv) is **generated** from the GitHub project
board — not from `pipeline.yaml` — and holds one row per tracked asset that has
a usable filepath:

```bash
python tools/pipeline/pipeline.py asset list             # the full report
python tools/pipeline/pipeline.py asset list --write     # regenerate the .tsv
python tools/pipeline/pipeline.py asset list --check     # fail if it has drifted
```

TSV has no comment syntax, so unlike `PIPELINE.md` the file cannot announce that
it is generated. Editing it by hand is pointless: the next `--write` reverts it.

Every column is board-derived on purpose. `status` is the board's own column and
never the delivery signals (`on_disk`, `delivered_by`) that the text and markdown
reports show, because those depend on which branch you have checked out — the
file would drift on `git checkout` and `--check` would report noise.

Unlike the other generated files here, `--check` is **not** a CI gate. It needs
the network and the `read:project` scope, which a workflow's repo-scoped
`GITHUB_TOKEN` cannot have.

## Open questions

`pipeline.yaml` carries an `open_questions` block per pipeline, rendered at the
bottom of `PIPELINE.md`. They are recorded rather than silently resolved because
guessing would bake a wrong answer into CI.

The asset root, the facing-direction axis and the three competing texture naming
conventions have all since been decided — `assets/art/3d/` for 3D with `assets/art/2d/` kept
as the 2D root, +Y forward in Blender becoming **−Z** in the exported glTF, and
`t_{asset_name}_{descriptor}` for textures. What remains open is only when
existing exporter-named textures migrate.

The +Y→−Z mapping was measured against a real export rather than reasoned about:
`assets/art/3d/example_cubes_facing` is a cube with a nub, the nub sits on Blender
+Y, and it lands on −Z in `sm_example_cubes_facing.gltf`. −Z is also Godot's
forward (`Vector3.FORWARD`), so the artist habit and the engine agree and
neither had to change. This deliberately does not match the glTF spec's own
+Z-front convention; see the `facing_direction_gltf` rule for why.

## Scope

Only the static 3D pipeline is `status: authoritative`. The 2D sprite and audio
pipelines are `status: stub`: they record what
`.github/scripts/validate-aseprite-files.py` and `validate-audio-files.py`
already enforce, and nothing more. Filling them in means documenting the
authoring phases and answering their own open questions first.
